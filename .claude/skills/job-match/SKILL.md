# job-match

把库里几百条职位收敛成「该投的几个 + 为什么 + 怎么谈」。

**分工先说清**，这决定了你该做什么、不该做什么：

| 谁做 | 做什么 |
| --- | --- |
| **CLI**（`job match` / `job shortlist`） | 打分、排序、薪资解析、去重 —— 可重跑、两次一样 |
| **Config**（profile 目录） | 简历、求职偏好、匹配信号表 —— 随人而变，一个 profile 一份 |
| **你**（这个 skill） | 读 JD 比硬门槛、判断投不投、排优先级、写投递口径 |

所以：**不要自己写打分脚本**。分数已经有了，你的价值在读 JD。
反过来也成立：**不要凭分数下结论**。分数只是分诊，第 1 名可能有硬门槛冲突，
第 8 名可能是最该投的。

## 第 0 步：确认用哪个 profile，再确认前提

运行按 **profile** 隔离：一个 profile = 一个人 / 一种求职场景，
简历、信号表、职位库都在它自己的目录里。挑错 profile 就是拿 A 的简历去比 B 的岗位。

```bash
uv run job profile list         # 有哪些、哪个是默认、各自多少条数据
```

只有一个就用它；有多个就**问用户这次挑哪条线的**，别默认。选定后所有命令带 `-p <名字>`。

```bash
uv run job -p <名字> config path --json   # 简历、信号表、数据库的绝对路径
uv run job -p <名字> config validate      # 简历、偏好、信号表是否就位
uv run job -p <名字> stats                # 库里有多少数据、抓了多少 JD
```

库是空的 → 先让用户跑 `job search` + `job detail`，别硬做。

**路径一律从 `config path --json` 取，不要按记忆拼 `config/resume.md` 这种路径**——
它们随 profile 变。下面用 `<resume>` / `<preferences>` / `<match>` / `<database>`
指代那份 JSON 里对应的字段。

然后**必读这两份文件**（它们是你全部判断的依据）：

- `<resume>`（profile 目录下的 `resume.md`）—— 候选人实际做过什么，有哪些数字
- `<preferences>`（profile 目录下的 `preferences.md`）—— 硬约束、薪资口径与底线、
  不看的岗位、面试口径

薪资一律是**税前**：JD 标的是税前，偏好里写的也应当是税前，两边直接比即可，
不用做任何换算。偏好里如果写的是税后数字，提醒用户改成税前，不要替他换算。

## 第 1 步：分诊

```bash
uv run job -p <名字> match --top 30 --why
```

`--why` 会打出每条的命中与扣分信号。扫一遍，判断**信号表本身准不准**：

- 明显不该进前列的岗位排很高 → `<match>` 缺一条负信号
- 明显该进的没进 → 缺正信号，或 `--floor` / `match.salary_floor_wan` 门槛太高
- 大面积「不含目标赛道关键词」→ `[require].pattern` 写窄了

**改 `<match>`（当前 profile 的 `match.toml`）再重跑，不要在分析里手工纠偏。**
手工纠偏这次能用，
下次跑又是老样子；改配置才是积累。改完告诉用户你改了什么、为什么。

## 第 2 步：生成清单骨架

```bash
uv run job -p <名字> shortlist --limit 12
```

产出 profile 的 `data/shortlist.md`（路径见 `config path --json` 的 `shortlist`），
里面每条岗位有三处 `<待 /job-match 填写>`：
**硬门槛核对**、**投不投**、**投递口径**。你的工作就是填掉它们。

## 第 3 步：逐条读 JD，填三处空

对清单里的每一条，先把完整 JD 读出来：

```bash
uv run job -p <名字> match --json | python3 -c "import json,sys;print([j['url'] for j in json.load(sys.stdin)][:12])"
```

JD 正文已经在库里，直接查比重新抓快（`<database>` 是 `config path --json` 给的库路径）：

```bash
sqlite3 "<database>" "select description from job_details where jobId = <id>;"
```

### 填「硬门槛核对」

逐条比 JD 的硬性要求与 `<resume>`。**差多少就写多少，不要含糊**：

- 「要求带 50 人+，候选人带 5 人实线」——写「差 10 倍」，不写「管理经验稍欠」
- 「要求 3 年算法/NLP，候选人是工程落地背景」——写清是哪一类经验缺失
- 「要求本体论 / 知识图谱且要完整落地案例」——这种特定技能缺失是硬墙，直说
- 学历、年限、985/211、语言这些能一眼比的，对得上就写「✓」，别占篇幅

区分**硬门槛**和**加分项**：JD 写「优先」「加分项」的不是门槛，别当墙。

### 填「投不投」

`投` / `观望` / `不投` + 一句话理由。判据按优先级：

1. **偏好里的硬约束**（base 地、明确不看的岗位类型）—— 违反就是 `不投`，没得商量
2. **硬门槛差距**是「差一点」还是「差一个量级」—— 后者即使内容极其对口也只能 `观望`
3. **薪资**够不够底线（税前对税前）—— 不够但方向极好，看偏好里写的放宽条件
4. **内容匹配度** —— 这一项最容易高估，因为 JD 都写得很漂亮

一份健康的清单里 `不投` 应该占不小的比例。**如果你把 12 条全判成「投」，
说明你没在判断。**

### 填「投递口径」

三件事，各一两句：

- **简历哪段最该往前放**：对着这份 JD，`<resume>` 里哪一段最该被先看到
- **大概率被追问什么**：JD 强调的、而简历里薄的地方，就是面试的靶子
- **薪资怎么报**：报多少（税前）、什么条件下能下探（照偏好里的底线）

## 第 4 步：排优先级，给结论

清单填完后，**在对话里**给用户一份收敛的结论（不是把 Markdown 念一遍）：

- **A 档（优先投）**：无硬门槛冲突 + 内容对口 + 薪资达标或接近
- **B 档（可投，有落差）**：写清落差是什么，以及为什么仍值得投
- **明确排除**：列出来并附一句原因——这样下次跑不会重复筛同一批

每档限 2–4 条。**给不出理由的岗位不要放进 A 档。**

再补两件用户自己看不出来的：

- **市场结构**：`uv run python scripts/track_stats.py --top 12` 看目标方向占大盘多少。
  「你的方向只占 17%」这种事实决定了策略是精投还是海投。
- **简历措辞体检**：把目标赛道 JD 的高频词和 `<resume>` 的措辞比一遍，
  指出「你有这个能力但没用市场的词」。这一步的产出通常比补技能更值钱。

## 边界

- **不投递。** `job apply` 不可撤销，除用户明确要求外绝不运行。
- **不编造。** JD 里没写的要求不要替它想；简历里没有的经历不要替用户圆。
  信息不足就写「JD 没写清，面试要问」。
- **不改简历事实**，只改措辞与顺序，且要告诉用户改了什么。
- **不写一次性打分脚本。** 要改打分就改当前 profile 的 `match.toml`——
  那才能跨会话复用。
- 判断写进当前 profile 的 `data/shortlist.md`，不要写进它的输入文件
  （`resume.md` / `preferences.md` / `match.toml` 是用户的输入，不是你的产出）。
- **只碰选定的那个 profile。** 别的 profile 可能是另一个人的东西。

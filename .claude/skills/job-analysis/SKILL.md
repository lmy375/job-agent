# job-analysis

把一个 profile 里采到的职位与 JD，变成**这一次要回答的那个问题**的答案。

**分工先说清**，这决定了你该做什么、不该做什么：

| 谁做 | 做什么 |
| --- | --- |
| **CLI / 内核** | 采集、JD 抓取、薪资文案 → 年薪区间、按 JD 正文去重、库存计数、关键词打分——事实，两次一样 |
| **Profile** | `resume.md`（他有什么）、`preferences.md`（他要什么）、`[score]`（他的取向）——**分析的角度从这里来** |
| **你**（这个 skill） | 定口径、切角度、读数、下结论、把结论落回配置 |

## 和 `job-align` 相反：这个 skill **要**写一次性脚本

`job-align` 明令不写统计脚本，因为那些统计在 `job align` 里。
**市场分析正相反：它刻意不在仓库里**（CLAUDE.md「不承担市场分析」一节，
`job report` 与整个 `core/analysis/` 已被整体删除）。理由是同一批 JD，
做算法的人想看框架分布，做管理的人想看汇报线与团队规模，换城市的人想看地域薪资差——
任何一种固定切法都只对写它的人有用。

所以：

- **脚本写在 scratchpad，不进仓库**，也不要往 `src/` 里加任何分析逻辑。
- **脚本里可以有「这条属于哪个方向」这种判断**——它是这次分析的一次性口径，
  不是仓库的功能。但**同一个判断不许写进 `src/`**。
- 只有当某样东西**换个人也一样**（去重、薪资解析、库存计数）才该在仓库里。
  发现缺了这类能力，报告给用户说「这该进 CLI」，别自己在脚本里长期养一份。

## 这个 skill 不绑定任何行业

下面的方法对「安全」「AI」「前端」「供应链管理」「临床医学」一样成立。
**具体是哪一行、哪些词算这一行、哪些方向算好方向，全部从这个 profile 的
`resume.md` / `preferences.md` / `[score]` 注释和用户这次的话里读**，
不能从你自己这里来。skill 正文里出现任何一个具体行业的取向都是 bug。

## 第 0 步：确认 profile，确认这次要回答什么

```bash
uv run job profile list                    # 有哪些、哪个是默认、各自多少条数据
uv run job -p <名字> config path --json     # profileFile / resume / preferences / database 绝对路径
uv run job -p <名字> stats                  # 库存：多少职位、多少 JD、打没打分、按关键词的分布
```

有多个 profile 就**问用户分析哪条线**，别默认——分析错 profile 等于拿 A 的数据
回答 B 的问题。选定后所有命令带 `-p <名字>`。

然后读 `<resume>` 与 `<preferences>`。**这两份文件决定你切哪些角度**：
简历里最重的那几段经历是「我有什么」，偏好里的优先方向与硬约束是「我要什么」，
分析的价值就在这两者与市场的差上。

最后**问用户这次要回答什么**，把它写下来。常见的几类，答案完全不同：

| 用户真正在问 | 该算的东西 |
| --- | --- |
| 「这个市场大不大、给多少钱」 | 规模 + 价格分位 + 门槛 |
| 「我该往哪个细分方向走」 | 细分方向切分 + 各方向的价格与量 |
| 「我的简历够不够、差在哪」 | 需求词频 ↔ 简历对照 |
| 「A 和 B 两条线哪个机会多」 | 跨 profile 同口径对照 |
| 「现在是不是好时候」 | 只有一次采集的话——**这个问题答不了**，说明白 |

**不要默认「做一份市场报告」**。九个角度都算一遍，产出是一堆没人读的表。

## 第 1 步：先量口径——搜到的条数 ≠ 这一行的岗位数

**这是整个流程里最重要的一步，也是最容易跳过的一步。**
职位搜索是宽匹配，回来的东西里有相当一部分根本不是这一行。
实测过一次：730 条里只有 279 条（38%）是真的那一行。
**不做这一步，后面每个百分比都是错的，而且错得看不出来。**

### 1.1 写下两组词

和用户一起定（词从他的话和 `preferences.md` 里来，不是你想的）：

- **纳入词**：这一行的岗位职位名里几乎一定会出现的词。
- **同形词陷阱**：同一个字面在**别的行当**里的意思。这是通例不是特例——
  任何一个行业词都有它的同形词，先花两分钟找出来：

  | 搜的词 | 同形陷阱（不是这一行） |
  | --- | --- |
  | 安全 | 安全生产 / 功能安全 / 消防 / 药物安全 / 行车安全 |
  | 算法 | 交易算法 / 排产算法 / 算法专利律师 |
  | 风控 | 金融风控 / 内容风控 / 施工风险控制 |
  | 产品 | 产品经理 / 产品安全 / 产品工艺 |
  | 运营 | 内容运营 / 安全运营 / 厂务运营 |
  | 平台 | 业务中台 / 招聘平台 / 电商平台运营 |

  规律：**一个词越常用，它的同形陷阱越多**。宽词（「网络安全」「人工智能」）
  最容易骗人，窄词（「二进制安全」「智能合约审计」）基本不会。

### 1.2 量出来，按关键词分开报

写脚本（骨架见 `references/angles.md`）算三件事：

1. 总条数 → 判为这一行的条数 → **准确率**；
2. **每个搜索关键词各自的准确率**（真岗数 / 该词回来的条数）；
3. 判错的抽样 20–30 条，**给用户看一眼**——清洗规则是这次分析的地基，
   地基由用户点头，不是你拍板。

第 2 项本身就是给用户的产出：它是关键词表该怎么改的**唯一实测依据**（第 6 步用）。

### 1.3 标注采样不全

翻一遍采集日志（`job search` 的输出）。任何一个关键词如果**撞了服务端返回上限**
（日志里会写「已达服务端上限，实际更多」），说明那一段**采样不全**——
偏偏撞上限的常常是最热的那个方向。这件事必须写进结论，不能默默用。

## 第 2 步：去重，报三个数

同一个岗位常被多家猎头重复挂出，正文一字不差、标价各挂各的（实测有一份挂了 8 次，
标价差 2–3 倍）。**用仓库的去重，不要自己写**：

```python
from job_agent.context import AppContext
from job_agent.core.dataset import load_rows
ctx = AppContext.create(profile="<名字>", configure_logging=False)
rows = load_rows(ctx.db, dedupe=True)     # 按 JD 正文去重，保留标价最高的那条，dupes 记重复次数
```

`load_rows` 顺带把薪资文案解析成了年薪区间（`salaryLow` / `salaryHigh`，万元、税前）——
**薪资也不要自己解析**，那有唯一正确答案，归仓库。

报告开头永远给三个数：**原始 N 条 → 这一行 M 条 → 去重 K 条**。
重复挂牌率本身是个结论（挂牌数比真实岗位数虚高多少）。

## 第 3 步：选角度，一次 3–5 个

角度菜单在 `references/angles.md`，每条都写了**怎么算**和**怎么读**。
按第 0 步用户的问题挑，**问一句他还想看什么**，别全算。

九类角度：规模与价格分位 · 细分方向切分 · 需求词频 · 供需结构 ·
门槛 · 交叉渗透 · 溢价在哪一段 · 跨 profile / 跨时间对照 · 简历 ↔ 市场差距。

三条通用的算法纪律：

- **用分位数，不用平均数。** 薪资是长尾，平均数被几个头部岗位拖着走。
  报 P25 / 中位 / P75 / P90，外加「≥用户底线的占比」——那个占比才是他关心的。
- **切分桶要互斥、先匹配先归属，并且必须报「其他」的占比。**
  「其他」超过三成说明桶没切对（多半是照你的想象切的，不是照这批 JD 切的）——
  回去看那三成里是什么，重切。
- **样本 <10 条的格子只报数、不解读。** 「这个方向中位数 90 万」在 n=6 时没有意义。

## 第 4 步：对照时必须同口径

跨 profile、跨时间、跨城市对照是最出洞见的角度，也是最容易骗自己的地方。
两边**任何一项不一致，都要先对齐再比**：

- **搜索薪资门槛**不同（一条线搜 ≥100 万、另一条搜 ≥80 万）→ 在共同的那一档上比；
- **清洗强度**不同（一边清洗过、一边是原始数据）→ 对另一边做**同等强度**的清洗再比。
  这个坑踩过一次：拿清洗后的 279 条比未清洗的 720 条，把「池子小 3 倍」算成了 2.6 倍；
- **采集时间**不同 → 写明各自的日期，差几周就别谈「趋势」；
- **关键词集合**不同 → 这一项通常对齐不了，那就明说「两边搜的词不同，量级可比、结构不可比」。

**一次采集不能谈趋势。** 「这个方向在涨」需要同一套关键词在不同时间各采一次；
没有第二次采集就不要写「正在增长」，只能写「当前存量里占多少」。

## 第 5 步：读数，出结论

- **口径写在结论前面**，不是脚注。读者先知道这 279 条怎么来的，才会信后面的话。
- **结论要回答第 0 步那个问题**，不是把表念一遍。每张表下面写一句「所以呢」。
- **「不存在」和「存在」一样是结论。** 某个方向只有 16 条、而且是所有方向里最便宜的
  一档——这比「AI 方向占 24%」对用户更有用，尤其当那正是他简历最硬的一块。
- **中位不动而尾部动，结论完全不同**：某个属性让中位数纹丝不动、却把「≥底线」的比例
  从 32% 抬到 44%，那它的作用是「能不能够到头部」，不是「普遍加薪」。别写成后者。
- **不要用常识补数据。** 没采到的就是没采到（没采上海就别谈上海，没有历史数据
  就别谈趋势）。库里没有的事实，一个字都不要写。
- 结论指向**行动**：该投哪一档、简历该改哪一句、下一轮该搜什么词。

## 第 6 步：回流——让这次的功夫下次还在

分析是消耗品，配置是资产。至少做前两条：

1. **把实测准确率写回 `[search].keywords` 的注释**，逐词标 `真岗数/总数`，
   停用的词注释掉并写明为什么停（留着比删掉好——下次才不会再犯同一个错）。
   改完 `uv run job -p <名字> config validate` + `search --dry-run` 验一遍。
2. **撞了服务端上限的词拆窄**，下一轮才采得全。
3. **发现的事实型门槛**（年限、学历、驻地这类读一眼就能判的）可以作为 `[score]`
   的候选信号报给用户——但**权重与取向由他定**，你只报事实。
4. **偏好里没写全的地方交还用户**：分析中发现一类岗位明显不该要但 `preferences.md`
   里没写，报告他去补，**不要替他写**。
5. 分析脚本留在 scratchpad。真觉得某一步下次还要做、且换个人也一样，
   那是 **CLI 该加的功能**，报告给用户，别把脚本留在仓库里假装它是。

## 边界

- **不改 `src/`。** 一行分析逻辑都不许进仓库——这是 CLAUDE.md 的硬规则。
- **不把任何行业的取向写进 skill 或脚本的注释里。** 取向只从这个 profile 读。
- **不编造数据**，不用常识补空缺，不把一次采集说成趋势。
- **不改 `resume.md` / `preferences.md`**；它们是用户的输入，有漏洞就报告。
- **不跑 `job llm-score`**（按条计费）、**不跑 `job apply`**（投递不可撤销）。
- **重新采集要先说代价**：受接口限流与详情页串行影响，几百条 JD 通常要几十分钟，
  先报时间再动手，别默默跑一小时。
- **只碰选定的那个 profile。** 别的 profile 可能是另一个人的东西。

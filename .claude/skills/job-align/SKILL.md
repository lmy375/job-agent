# job-align

拿模型读 JD 打出的分当**参照**，给关键词信号表（profile.toml 的 `[score]` 段）体检并校准。

**分工先说清**，这决定了你该做什么、不该做什么：

| 谁做 | 做什么 |
| --- | --- |
| **CLI**（`job align`） | 秩相关、窗口召回、逐条信号命中均分、子模式拆分、漏网 / 误报清单、候选正则探针——统计，两次一样 |
| **Config**（profile 目录） | `[score]` 信号表是用户的取向，一个 profile 一份；你改的就是它 |
| **你**（这个 skill） | 读统计判断「这条信号为什么乱命中」「漏网的岗有什么共同点」，决定砍哪条、加哪条、权重调到几，并解释理由 |

所以：**不要自己写统计脚本**——统计已经在 `job align` 里，两次跑出来一样，
你现写的不会。反过来也成立：**不要让数字替你决定**。「Δ 是负的就删」是机械操作，
不是校准；每条改动都要能说出「这个词在什么语境里出现、为什么不代表岗位本质」。

这个 skill 对**任何 profile** 都成立：做算法的人信号表里「预训练」是 +12，
做工程的人是 −12，方法一样——看命中它的岗位模型给几分。
**不要把任何一个方向的取向写进你的判断里**，取向只从这个 profile 的
`preferences.md` 和现有 `[score]` 注释里读。

## 第 0 步：确认 profile，确认前提

```bash
uv run job profile list          # 有哪些、哪个是默认
uv run job -p <名字> config path --json   # profileFile / preferences / database 的绝对路径
uv run job -p <名字> stats       # 「LLM 打分 N/M」那行：覆盖了多少、口径混不混
```

只有一个 profile 就用它；有多个就**问用户校准哪条线**，别默认——校准错 profile
就是拿 A 的模型判断去改 B 的信号表。选定后所有命令带 `-p <名字>`。

前提有两条，缺一条就先停：

- **LLM 分数够多。** 参照样本太少，统计全是噪声。经验上 view（去重、过薪资门槛）
  里有 LLM 分的至少 100 条，且**不只覆盖关键词排名前列**——只打了前 30 条，
  就永远看不到「关键词排 200 名但模型认可」的漏网。不够就告诉用户要补打多少条
  （`job llm-score --top N` 或 `--all`），**按条计费，由用户决定打不打**，不要替他跑。
- **口径统一。** `job align` 开头会警告「混着 N 种口径」——库里有换过模型或改过提示词
  的分数，互相不可比。先让用户决定是 `--force` 统一重打还是接受噪声。

然后读 `<preferences>`（用户的取向）和 `<profileFile>` 里 `[score]` 段的注释
（每条信号为什么存在）。**你判断的标尺是用户写下来的期望**，不是模型：
模型只是在读同一份偏好，它也会读错（见第 4 步）。

## 第 1 步：整体诊断

```bash
uv run job -p <名字> align --top 100
```

分数线默认对齐内置提示词的锚点（认可 = 吸引力 ≥7 且匹配 ≥5；明确不看 = 吸引力 ≤4）。
用户改过 `score_appeal.md` / `score_fit.md` 的锚点就用 `--appeal-floor` / `--fit-floor`
/ `--low` 跟着改。`--top` 是「用户实际会翻到第几名」——问一句，别猜。

先看三个数，它们是校准前后要比的：

1. **窗口召回**：前 `top` 名里模型认可的有几条 / 总共几条。这是关键词分诊的
   全部意义——把该看的送进视野。
2. **明确不看的漏进窗口几条**：误报。通常很少；多了说明某条正信号在乱加分。
3. **Spearman**：整体单调性。分档表能看出是哪一段不单调。

## 第 2 步：逐条信号体检

报告的信号表里每条给了：命中数、标题命中数、命中均分、Δ（命中 − 未命中）、
认可率、不看率。**黄色**的是可疑的：Δ 与权重方向相反，或 |Δ| < 0.3 且命中 ≥5。

按这个顺序判：

- **方向反了**（正信号 Δ<0 或负信号 Δ>0，命中数够多）：几乎一定是词选错了。
  典型：给某种技术栈扣分，但 JD 里列的是「Java / Python / Go 任一」，
  命中的反而是多语言工程岗。
- **不区分**（|Δ| 小、命中很多）：词太通用。典型：「从 0 到 1」「团队管理」「模型训练」——
  好岗坏岗都写。正信号降到象征性权重，负信号砍掉或只留岗位本质词。
- **区分但命中太多的负信号**：可能只有部分子模式在起作用。用 `--split` 拆开：

```bash
uv run job -p <名字> align --split | grep -A20 "<信号名>"
```

  子模式表按命中数排，看哪几个词的均分接近全库均分——那几个就是噪声。
  拿不准某个词在什么语境里出现，用探针看快照：

```bash
uv run job -p <名字> align --probe '安全合规' --context
```

- **命中太少（<5）**：不要按数字调它。样本不够，留着或按用户注释里的理由处理。

判断时的两条经验，对任何方向都成立：

- **负信号只写「岗位本质」的词，不写「技术栈提了一句」的词。** 「与 XX 团队合作」
  「熟悉 XX 者优先」里的词不代表岗位是什么。
- **通用词不区分，深水区的词才区分。** 搜索关键词本身（它命中六成职位）不会帮排序，
  只有真在做这件事的团队才会写进 JD 的词才会。

## 第 3 步：读漏网与误报

```bash
uv run job -p <名字> align --why | sed -n '/^漏网/,/^探针\|^下一步/p'
```

漏网清单每条带关键词命中 / 扣分和模型的依据。找**共同点**，不是逐条修：

- 一批漏网被同一条负信号压着 → 回第 2 步看那条信号。
- 一批漏网的头衔有共同词（「架构师」「Infra」「研发工程师」）而现有信号表没有
  → 候选新信号。**先探针再加**：

```bash
uv run job -p <名字> align --probe '(?a:\bai)\s*(架构师|architect)' --probe 'agent\s*infra'
```

  标题命中与正文命中分开报——权重会被 `title_multiplier` 放大，标题命中的均分
  才决定这条头衔信号值几分。**标题命中 <5 条的不要加**，那是给一两个岗位定制。

- 漏网的模型依据里反复出现同一种硬门槛（「要求 10 年以上」「要求博士」）
  → 候选负信号。这类**事实型门槛**（年限、学历、驻地）可以进信号表；
  「经验不够深」这种要读上下文的不行——它是判断，归模型。

误报（进了窗口但模型明确不看）通常很少。有就看它被哪条正信号抬上来的，
多半是那条正信号的某个子模式太宽。

## 第 4 步：模型也会错——把偏好的漏洞交还给用户

模型是照 `preferences.md` 判的。漏网里如果有一类岗位**用户明显不想要、但偏好里没写**
（偏好只写了「不看安全岗」，模型就会给产品经理岗 8 分），那不是信号表的错，
是偏好没写全。**报告给用户，让他补 preferences.md，不要替他写**，也不要为了
迎合模型删掉信号表里那条负信号——那条负信号是用户在替偏好补判断。

反过来，信号表里某条正信号命中的岗位模型一致给低分（比如「Web3 背景可复用」
命中的全是 Crypto 公司、模型 1.5 分），先查偏好：偏好里若写了不看好这个行业，
那条正信号就是在跟用户自己的偏好打架，可以删；偏好没写，就问用户。

## 第 5 步：改信号表、复测、定稿

改 `<profileFile>` 的 `[score]` 段。规矩：

- **正则用单引号**（TOML 字面量字符串）；英文缩写裹 `(?a:...)`；
  保持「一条信号一行正则、顶层用 `|`」——`--split` 靠它拆。
- **注释跟着改。** 每条改动写一句为什么（「去掉了 X：命中 N 条均分 M，多是……语境」），
  下次校准的人（或下次的你）要能看出这条是数据驱动改的还是拍脑袋改的。
- **不动 `[score]` 之外的任何内容**；不动 `salary_floor_wan`（它是看的门槛，不参与打分）。
- **一次改一批，改完立刻验：**

```bash
uv run job -p <名字> config validate
uv run job -p <名字> align --top 100
```

  比第 1 步的三个数。召回上去、误报没涨、Spearman 没掉，就是进步。
  某条改动让召回掉了就回退它——**不要为了一个数字连调三轮**，
  样本就几百条，调到第三轮已经是在拟合这批 JD 而不是在校准取向。

- 定稿后刷新库里的分数，Web 与 `job stats` 才看得到：

```bash
uv run job -p <名字> score -n 20 --why
```

- **在对话里给用户一份收敛的结论**：前后三个数的对比表、改了哪几条及各自的依据、
  第 4 步里要他自己决定的偏好问题。别把 `job align` 的输出念一遍。

## 边界

- **不写一次性统计脚本。** 统计缺什么就说缺什么——那是 `job align` 该加的功能，
  不是 scratchpad 里该出现的 Python。
- **不改 `src/`。** 这个 skill 改的只有 profile.toml 的 `[score]` 段。
- **不改 `resume.md` / `preferences.md`。** 它们是用户的输入；偏好有漏洞就报告。
- **不跑 `job llm-score`。** 按条计费，由用户决定打多少。
- **不把任何方向的取向写进判断里。** 「Agent 是好方向」「Java 是差栈」这类话
  只能从这个 profile 的偏好和注释里读出来，不能从你自己这里来。
- **只碰选定的那个 profile。** 别的 profile 可能是另一个人的东西。
